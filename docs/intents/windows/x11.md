# X11 windows

> Owns what an X11-only application gets: Xwayland, and the X11 window as a
> view. What a view is and how it behaves is
> [window-management.md](window-management.md); its title bar is
> [title-bars.md](title-bars.md).

## Requirement

An application that speaks only X11 runs in this session and its windows
are windows like any other: a title bar with minimize, maximize and close,
a place on the canvas, membership of a desktop, the overview, the window
states. A machine without Xwayland simply has no X11, and the compositor
runs the same.

## Design considerations

- **One View, two shells.** The canvas, the renderer, the input path and
  the capture path know only `View`; what differs between an xdg toplevel
  and an X11 window — the configures, the close, the title, the first
  commit — is answered twice, in `view_xdg.cpp` and `view_x11.cpp`, and in
  nowhere else. A reader of the canvas code never meets a protocol.
- **Xwayland starts with the first X11 client**, not at login: a session
  with no X11 application pays nothing for it.
- **X11 windows are decorated by us.** There is no decoration protocol to
  negotiate with: the window manager decorates, and here that is the same
  title bar every other window gets.
- **X keeps its own picture of the windows, and that picture decides the
  pointer.** Xwayland hands a pointer event to the X11 window that X's own
  stacking order and window positions put under it, not to the surface the
  compositor sent it to, and it keeps its pointer inside its own screen,
  the outputs' layout box. A dialog X stacks under its window, or a window
  X has off its screen, never sees a click. So the picture follows the
  canvas: X's stack is the canvas's, and every X11 window's X position is
  its canvas position less one offset shared by all of them. The offset
  follows the pointer wherever it is on the canvas, moving whenever X's
  pointer would leave X's screen, and every X11 window moves with it; one
  offset for all keeps them where they are relative to each other, so a
  menu its client puts beside its window lands beside it on the canvas.
  X hears of a move on its own connection and of the pointer on Xwayland's
  wayland one, so a pointer event can reach it before the move it needs:
  that event is told again a frame later. Keys need none of this: they
  follow the X input focus, which goes with the focused window.

## Behavior

| Subject | Rule |
|---|---|
| Starting | the compositor creates the X server lazily and exports `DISPLAY` for the clients it starts; the server itself starts with the first X11 client |
| A window | a view: placed where the user is looking, with a title bar carrying the X11 title, on the desktop it opens on |
| Input | clicks and keys reach the client as they reach any window, at the point drawn under the pointer, at any zoom and anywhere on the canvas; focus follows the same click-to-focus rule ([../input/keyboard-and-pointer.md](../input/keyboard-and-pointer.md)) |
| X's stacking order | the canvas's: a window that maps or is raised is on top in X too, a minimized one at the bottom |
| X positions | canvas positions less the shared offset, sent whenever a window is placed, moved or resized. At 100 % and closer the offset puts X's pointer where the cursor is; zoomed out, where one window can be larger than X's screen, the offset moves to put X's pointer back in the middle of the screen once it comes within `config::x11_pointer_margin` of an edge |
| States | maximize, minimize, fullscreen and tiling are told to the window through its X11 state and its configure; what the window asks for at map time is honoured |
| Close | the title bar's × asks the window to close itself through `WM_DELETE_WINDOW` |
| Capture and sharing | an X11 window is captured like any other window ([../apps/capture.md](../apps/capture.md)) |
| An override-redirect window | a menu, a tooltip or a drag icon: placed where its client puts it, through the same offset, beside the window it belongs to, with no title bar, no entry in the window list and no focus taken from the window |
| The clipboard | both ways: what an X11 client copies pastes in a wayland client and the other way round, through the seat's own selection |
| Without Xwayland | the compositor says so once at start and runs on; X11 applications do not start |

## Error states, corner cases

- **A window that never gets a surface** (an X11 window exists before its
  wayland surface): it is not on the canvas until the two are paired, and
  a window whose surface goes away leaves the canvas with it.
- **A window larger than X's screen** (maximized on a zoomed-out desktop)
  takes the pointer over its whole surface: the offset moves as the
  pointer crosses it, and the client is told each move as a move of its
  window.
- **A jump of the pointer** into a part of a window X's screen does not
  reach — the camera moved under the pointer, a window opened under it —
  lands on X's screen edge until a frame later, when the window is told
  the pointer's place again: a click after the jump lands where it was
  aimed; only a press in that same frame lands at the edge.
- **Positions X cannot hold**: X positions are 16-bit, so a window farther
  than that from the pointer waits at the limit; the pointer is nowhere
  near it.
- **Several outputs**: X's screen is their layout box, and the offset
  follows the pointer over any of them.
- **`WLR_XWAYLAND` naming a binary that is not there**: no X server, and
  the compositor keeps running.

## Out of scope for now

- **Hi-dpi**: an X11 window is drawn at scale 1 and enlarged on a scaled
  output — right-sized, a little soft
  ([../render/hidpi.md](../render/hidpi.md)). Named here so a later change
  honours it rather than inventing its own rule.
